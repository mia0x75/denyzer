# Repository Guidelines

Guidelines for AI coding agents working in this repository.
This is the Denyzer UI dashboard (Next.js static export) for the [Denyzer DNS proxy](https://github.com/mia0x75/denyzer). It is embedded into the Go binary: build it from the repository root with `make dashboard`, then `make build`.

## Project Structure

```
src/
├── app/                    # Next.js App Router
│   ├── layout.tsx         # Root layout
│   ├── icon.tsx           # App icon
│   ├── page.tsx           # Guarded dashboard shell + header doc links
│   └── login/page.tsx     # Administrator login
├── components/
│   ├── ui/                # shadcn/ui components (generated, do not edit)
│   └── dashboard/         # App-specific components
├── hooks/                 # Custom React hooks (use-*.ts)
├── lib/                   # Utilities (api.ts, api-types.ts, constants.ts, utils.ts)
└── styles/globals.css     # Global styles (Tailwind v4)
```

## Build, Lint, and Test Commands

```bash
make dashboard               # From repo root: install deps, static-export, copy to web/dashboard
bun run build                # Production static export (outputs ./out)
bun run dev                  # Start dev server (Next.js + Turbo)
bun run start                # Serve an existing build
bun run lint                 # Run ESLint
bun run lint:fix             # Run ESLint with auto-fix
bun run format:check         # Check Prettier formatting
bun run format:write         # Auto-format with Prettier
bun run typecheck            # TypeScript type checking
bun run test                 # Auth, guard and statistics tests (node:test via Bun)
bun run verify               # Tests + lint + format + typecheck + knip + checkdupe
bun run knip                 # Detect unused exports and dependencies
bun run checkdupe            # Detect code duplication (jscpd)
```

After any code change, always run `bun run lint`, `bun run format:check`, and `bun run typecheck` to validate.

## Code Style Guidelines

### TypeScript

- Strict mode with `noUncheckedIndexedAccess` enabled
- Use inline `type` imports: `import { type Foo } from "bar"`
- Prefix unused parameters with underscore: `(_unused) => {}`
- Never use `any`; prefer `unknown` when type is truly unknown
- Do not use non-null assertions (`!`) or type casting to bypass errors

### Imports

- Use the `~/` path alias for all src imports: `import { cn } from "~/lib/utils"`
- Use inline type imports: `import { type ComponentProps } from "react"`
- Never import directly from `clsx`; use `cn` from `~/lib/utils` (enforced by ESLint)

### Naming Conventions

- Component files: `kebab-case.tsx` (e.g., `server-status.tsx`, `query-tool.tsx`)
- Component names: `PascalCase` (e.g., `export function ServerStatus()`)
- Hook files: `use-*.ts` (kebab-case with `use-` prefix) in `src/hooks/`
- Types/interfaces: `PascalCase` (e.g., `LogEntry`, `FilterValue`)
- Constants: `UPPER_SNAKE_CASE` for arrays/enums (e.g., `TIME_RANGES`)

### React Components

- Use function declarations with named exports (not `React.FC` or arrow functions)
- Add `"use client"` directive only when needed (hooks, browser APIs, event handlers)
- Destructure props in the function signature

```tsx
// Good
export function MyComponent({ title, onClick }: MyComponentProps) {
  return <button onClick={onClick}>{title}</button>;
}

// Avoid
export const MyComponent: React.FC<MyComponentProps> = (props) => {
  return <button onClick={props.onClick}>{props.title}</button>;
};
```

### Styling

- Use Tailwind CSS classes exclusively (v4, CSS-based config in `globals.css`)
- Use `cn()` from `~/lib/utils` for conditional class merging
- Tailwind classes are auto-sorted by `prettier-plugin-tailwindcss`

### Data Fetching

- All data comes from the Denyzer Go API over relative `/api/...` and `/debug/...` paths (same origin).
- Use `@tanstack/react-query` hooks in `~/lib/api.ts` for queries; no tRPC.

```tsx
const { data, isLoading } = useQuery({ queryKey: ["blocking-status"], queryFn: fetchBlockingStatus });
```

### Error Handling

- Use try/catch for async operations that may fail
- Provide user-friendly error messages
- Use `toast` from `sonner` for user notifications (`toast.success()`, `toast.error()`)

### shadcn/ui Components

Components in `src/components/ui/` are generated by shadcn CLI. Ask for permission before editing.
If a component exists in shadcn, add it instead of creating one manually:

```bash
bunx shadcn@latest add <component-name>
```

When doing so, be careful with the --overwrite flag, since some components may have manual changes, which would break by replacing them with that flag.

## Formatting & Linting Rules

- 2-space indentation, LF line endings
- Report unused ESLint disable directives

## Data Flow

The dashboard is a static export served at `/` on Denyzer's separate HTTPS management listener (`ports.admin`), with login at `/login/`. It talks to `/api/logs/query` and `/api/stats/...` on the same origin. The public HTTP/HTTPS/HTTP3 DoH listeners do not serve management routes. No environment variables or runtime config are required.

Authentication uses an in-memory, fixed seven-day Bearer session. Keep the token in `sessionStorage` and use `~/lib/auth.ts` for authenticated fetches and centralized 401 handling. `GET /api/login` returns the token held by the page cookie, so a new tab or a restarted browser adopts the existing session. Only a 401 clears the session; transport failures, HTTP server errors and cancelled requests keep it. Do not retry mutations. The Secure, HttpOnly page cookie authenticates page requests only, never API/debug requests, and lives as long as the session. The dashboard guard signs out only when the status requires a token or never answered; the login page must not redirect to itself.

Never commit secrets.

## Git Workflow

The dashboard lives in the main Denyzer repository (no separate repo). Ensure `bun run lint`, `bun run format:check`, and `bun run typecheck` pass before pushing.
